## 공통 점유와 실제 지원 범위

작성·저장·공개·야간 교류·수기 작업은 최신 점유를 공유한다. 어느 경로든 브라우저 조작 전
최신 전체 외부 원장 버전·실행 ID·소유자·진행 상태를 읽고, 실제 지원되는 버전 조건으로
점유를 선기록한다. 먼저 진행 중인 작업은 유지한다. 야간 교류는 남은 회차 안에서5분 간격으로 점유를 재확인하고 대기시간도 원래 마감에 포함한다. 충분한 잔여시간과 해제증거가 없으면 제출0·미실행으로 기록한다. 다음회차와 겹치거나08시회차가09시를 넘지 않는다.
버전 충돌·점유 불명·기록 실패는 클릭하지 않는다. 자신의 실행 ID만 해제한다.
수기 작업도 같은 점유 확인에 참여하며 별도 탭으로 충돌을 피했다고 간주하지 않는다.

로컬 SQLite/파일 잠금과 GitHub workflow의 concurrency는 다른 Work 세션까지 잠그지 않는다.
`work-operation-v1`은 수기 요청의 지속 기록·재실행 방지이며 **분산 브라우저 잠금이나 강제 종료가 아니다.**
외부 원장의 버전 조건 지원이 확인되지 않으면 해당 브라우저 쓰기는 보류한다. API-only 준비는
독립적으로 진행할 수 있지만 미해결 수기 편집/저장이 있으면 새 저장·공개 인계는 보류한다.
인증·CAPTCHA·명시적 도구/권한 거절을 다른 경로로 우회하지 않는다.

## 수기 예외의 공통 기록

육아·운동·투자·유래·요리 모두 명시적 수기 Work 요청을 등록할 수 있다. 이 경로는 메타데이터만
기록하며 원고/이미지를 생성하거나 API를 호출하거나 네이버를 클릭하지 않는다.
기존 `manual-request-v1`의 유래 유료 준비와 날짜/원고가 고정된 복구는 각 승인 범위를 유지한다.
새 공통 기록이 그 유료 경로의 카테고리·예산·재시도·발행 권한을 확대하지 않는다.

실제 사용자 메시지에서 작업을 확인한 운영자가 비공개 JSON에 다음 필드를 모두 기록한다:

- `version="work-operation-v1"`, 고유 `operation_id`, 원래 원고의 `request_id`, 실제 `category`.
- `action="create"|"revise"|"save"`, `approved_by="repository_owner"`, 실제 KST `approved_date`.
- `approval_reference`: 실제 소유자 메시지에 연결한 `Sentinel_...` 참조. 문자열 자체가 승인 증거는 아니다.
- `scope="draft_only"`. 공개 발행은 별도 기존 승인·당일 발행 한도를 확인하며 이 경로에는 발행 명령이 없다.
- `target_sha256`: 수정/저장할 검증 원고 파일의 SHA-256. 신규 작성만 빈 문자열이다.

본문·사진·키·사적 설명은 이 메타데이터에 넣지 않는다. 실제 대상 목록·원고·해시·외부 점유를
확인한 뒤 동일 비공개 `BLOG_DATA_DIR`에서 실행한다:

```text
blogbot register-manual-work --file <private-manifest.json>
blogbot start-manual-work --operation-id <ID> --target-sha256 <verified-hash>
blogbot finish-manual-work --operation-id <ID> --file <private-observed-result.json>
blogbot manual-work-status
```

신규 작성의 start는 `--target-sha256`를 생략한다. 시작은1회이며 날짜 변경·내용 변경·다른 진행/불확실
작업이면 시작하지 않는다. 등록된 원고는 자동 준비·미디어 재개·저장·발행 후보에서 제외한다.
수기 결과는 `work-operations/<operation_id>.json`에 보존하고 자동 `posts/attempts/save_receipts`
한도를 추가/초기화하지 않는다. 기존 자동 원고를 수정할 때 기존 ID·최초 저장/발행 이력은 보존한다.
수기 수정·저장을 완료했다고 원래 자동 승인 본문이 아직 유효한 것으로 해석하지 않는다.

실제 결과 JSON은 `outcome`, `content_sha256`, `evidence_ref`, 시간대 있는 실제 `checked_at`이다.
작성/수정 완료는 `COMPLETED`, 저장 완료는 `SAVED_NAVER`와 실제 `saved_at`을 추가한다.
미확인 저장은 `SAVE_UNCERTAIN`이며 다시 start/클릭하지 않는다. 미제출/오류는 `HELD`로 보존하고
편집/저장 결과가 불명확하면 자동 쓰기를 막는 상태를 유지한다. 저장 부재 종결은 `SAVE_NOT_SAVED`와
기존 영수증 계약의 `save_check`(원래 시도시각, 실제 소유 초안/공개 목록 부재, 확인시각·증거)를 요구한다.
나중의 저장 확인은 실제 읽기 증거로만 종결한다. 확인시각을 최초 저장시각으로 대신하지 않는다.

같은 완료 결과를 기록하는 것은 멱등적이며 작업 재실행이 아니다. 오래된 bundle의 REGISTERED/STARTED가
최신 완료·불확실 기록을 덮지 못한다. 수기 기록은 암호화 bundle에 포함하며 복원 시 일관성을 확인한다.
외부 Work 세션의 새 기록이 다음 API 준비에 자동 전달되는 연결은 없다. 기존 암호화 인계와 외부
원장 전달을 완료한 뒤 소비 여부를 확인한다. 등록·코드 배포만으로 실제 요청 소비 완료를 보고하지 않는다.

수기 임시저장 증거에 `operation_id`/`mode="manual"`이 있으면 일반 `records`에 넣지 않는다.
새 공통 수기 저장은 위 finish 명령으로 기록하며 v1 유래의 `additional_records`는 기존 절차를 유지한다.
수기 임시저장 수 제한 예외는 공개 발행 수 제한 예외가 아니다. 모든 실제 공개 발행은 수동 공개까지 합산해
RESET_OPERATIONS의 현행 날짜·stage별 일/주 한도를 적용한다. 수기 공개는 원장·공개 목록·별도 승인 범위를 확인하는 기존 Work 절차로만 처리한다.
실제로 공개된 수기 글은 소유자 공개 URL·글 ID·실제 발행시각·원래 저장일을 검증한 `PUBLISHED`
영수증으로 일반 `records`에 반영할 수 있다. 이는 관측 기록일 뿐 발행 허가가 아니며 공통 당일
발행 한도를 소비한다. 수기 임시저장의 예외를 공개 글 집계 누락으로 확대하지 않는다.

과거 공개글의 발행일만 실제 확인된 경우에는 한도 집계 누락을 복구하는 관측 영수증으로만
`status="PUBLISHED"`, `published_at=""`, `published_at_precision="day"`를 허용한다.
기존 `request_id`·`day`(최초 저장일)·카테고리·소유자 공개URL·글ID를 유지하고, 입력의
`publication_check`에 `published_date`, `timezone="Asia/Seoul"`, `published_post_checked=true`,
시간대 있는 실제 `checked_at`·원장/화면 `evidence_ref`를 넣어 기존 `publication_check_json`에 보존한다.
저장일≤공개일<오늘인 과거 공개만 대상이며, 관측시각은 공개일 당일 또는 이후·현재 이하로 검증한다.
임의00:00이나 관측시각을 발행시각으로 채우지 않고, 기존 정밀 발행시각 덮기·발행 시도 불확실 상태
해제·최초5편 증량 실증 근거로 사용하지 않는다. 정확한24/72시간 경과 확인도 이 날짜로 대신하지 않는다.
기존 저장·시도 이력을 보존하며 실제 공개 목록과 일/주 한도 집계를 대조한다. import·암호화 인계·복원은
각각 실제 결과를 확인한 뒤 최신 원장의 시행 영수증에 기록하며, 코드 지원만으로 일치·복원 완료를 주장하지 않는다.

## 저장 완료 이후 읽기 검수 — post-save-review-v1

콘텐츠 개선안의 추가 증거·별도35점 진단은 [CONTENT_QUALITY의 editorial-evidence-v2와 dia-content-diagnostic-v1](CONTENT_QUALITY.md#내용차별성-증거--editorial-evidence-v2)을 따른다. 기존 원고/저장본 점수·영수증 상태·실행 스키마는 그대로 유지한다. 신규/수정은 원래 요청·작업 유형과 실제 결과 게시물 ID를 대조한다. 수정은 기존 ID 유지 여부, 신규는 새 ID와 비교 기존 ID를 확인하며 제목·날짜만으로 구분하지 않는다. 현재/이전 제목 이력·공개 URL·실제 최초 발행/수정시각은 관측 정밀도만 기록하고 목록 날짜로 정확한 시각을 추정하지 않는다.

최신 입력은 실제 합성 기준과 Work 수령 버전을 확인한다. 중단 복구용 저장 프롬프트·기존 캐시는 소급 갱신하지 않는다. 과거 입력과 현재 기준의 차이는 기존 비공개 인계에서 확인하고, 원고를 다시 구매하거나 자동 공개 수정으로 메우지 않는다.

SAVED_NAVER와 실제 저장 증거 보존 직후 [CONTENT_QUALITY의 저장본 품질평가](CONTENT_QUALITY.md#임시저장-후-품질평가보완재평가--post-save-review-v1)를 적용한다. 저장 후 실물 평가 → 별도 보완 → 수정 저장 확인 → 재평가 → 보고를 원래 원고 ID로 연결한다. 평가 기록은 기존 원고 심사·저장 영수증과 별개이며 DB enum이나 공통 manifest 필드로 주입하지 않는다. 필수 실물 확인을 위한 실제 저장본 재열기는 기존 점유와 승인 범위에서 수행하되, 읽기 평가를 위한 가짜 save 작업·새 유료 호출·발행은 하지 않는다. 미확인 항목은 미산정으로 남기고 기존 점유·수기 기록·일정·저장 한도·발행 권한을 유지한다.

## 상태·알림·측정

`run-summary.json`은 기존 `failed`/exit 동작을 유지하면서 `outcome`과 `deliverable_ready`를 추가한다.
입력 대기는 `WAITING`, 구성/검수/저장 확인 필요는 `NEEDS_ACTION`, 실제 처리 오류는 `ERROR`,
당일 전달 가능한 승인 원고는 `READY`, 성공한 진단은 `DIAGNOSTIC`이다. WAITING/DIAGNOSTIC을
원고 준비·네이버 저장·발행 성공으로 보고하지 않는다. 실제 실패를 입력 대기로 낮추지 않는다.

일상 진행·정상 발송 알림은 생략하고 중요한 결정·신규 장애·요청된 최종 보고만 전달한다. Telegram은 명시적 `BLOG_NOTIFY_ENABLED=true`와 기존 토큰·수신자
설정이 있을 때만 사용한다. 새 수신자·테스트 메시지를 보내지 않는다. `blogbot doctor --runtime`은
비밀값 없이 현재 계약·수기 상태·자동수집 설정·알림 구성 여부를 읽는다. Work의 자율 주제 선정은
[CREATOR_TRENDS](CREATOR_TRENDS.md)에 따라 최신 유효 Creator Advisor 자료를 확인하고 선정 키워드 실제 검색·상위 본문3~5개 벤치마킹을 거친다. 과거 자동수집 중단을 이 읽기 절차의 금지로 해석하지 않으며, 오래된 자료의 날짜 변경·신규 유료 수집·별도 예약은 하지 않는다.

현행 당일 실물·익일 통계·발행/최종수정 후24/72시간 관측과 D0~D6·D0~D27 평가는 RESET_OPERATIONS를 따른다. 아래 첫 코호트는 과거 측정 이력이며 새 발행 대기 조건이 아니다.

첫 코호트10/12~25의 글마다 **실제 발행일을 KST로 환산한 D0~D6의7개 달력 일자**를 비교한다.
`measurement_post_days=7`/`measurement_window="kst_calendar_days_d0_d6"`가 기준이고,
legacy `measurement_post_hours=168`은 보고용 명목값이지 발행시각부터168시간 조회 조건이 아니다.
마지막10/25 글의D6은10/31이고 집계 확인·검토는11/1 이후다. `measurement.post_window`는 실제
시간대/정밀도가 있는 발행시각만 받으며 관측시각·미확인 발행시각을 대신 쓰지 않는다.
집계 지연·미제공 지표는 미확인으로 둔다. 이 측정 기준은 주간 계획의 만료/자동 복귀를 만들지 않는다.
