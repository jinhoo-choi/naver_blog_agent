# Creator Advisor를 먼저 참고하는 주제 선정 절차

구현 버전: `creator-advisor-v1` · UI 확인: 2026-10-05 KST

## 실제로 확인한 화면과 숫자의 뜻

[써누애비 Creator Advisor 트렌드](https://creator-advisor.naver.com/naver_blog/choijku/trends)에서 로그인된 화면을 확인했다.

- **검색 유입 트렌드 → 주제별 인기유입검색어**: 육아·결혼 등 주제별 검색어 목록이다. 사용자 제공 10월 4일 화면의 `▲26`, `▼3`, `new`, `-`는 조회수가 아니다. 캡처된 목록의 순서는 `keyword_inflow_order`로만 기록한다. 순위 변화 숫자를 현재 순위로 입력하지 않는다.
- **검색어 클릭 → 인기 검색어 트렌드 → 이 검색어로 유입된 게시물**: 번호가 붙은 게시물 제목과 URL이 보인다. `search_inflow_rank`로 기록한다. 개별 게시물 조회수는 보이지 않아 `views: null`이다.
- **메인 유입 트렌드 → 네이버 메인에서 많이 유입된 콘텐츠**: 전체 주제의 유입 순서다. `main_inflow_rank`이며 전체 인기 연예 글을 육아 주제로 자동 선택하지 않는다.
- **주제별 트렌드 → 조회수**는 주제 단위 차트다. 이를 개별 글 조회수로 쓰지 않는다.
- 조회 당시 메인 날짜는 10월 3일, 열린 검색어 상세 화면은 10월 2일을 표시했다. URL의 날짜나 오늘 날짜를 대신 넣지 말고 **각 실제 목록 위에 표시된 날짜**와 최종 관찰 URL을 함께 보존한다. 날짜가 서로 다른 화면은 별도 그룹으로 기록한다.

이 순위는 검색노출 순위·검색량·저경쟁·상위노출 보장이나 사실 검증의 증거가 아니다.

## 주제 결정 전 실행 순서

1. 당일 편성, 소유자 지정 주제/수동 초안, 실제 질문·자료, 금요일 KIS 적격 자료를 먼저 확인한다. 하루 1편, 육아5·수요일 운동1·금요일 투자1, 새 자료가 있을 때만 가족 AI를 유지한다.
2. **기존 09:00 KST 준비 실행 전** 로그인된 Creator Advisor 화면에서 해당 주제의 최신 표시 날짜와 검색어를 확인한다. 육아는 육아·결혼, 운동은 스포츠/건강·의학, 투자는 비즈니스·경제를 사용한다. 필요한 필터가 없으면 계정 설정을 조용히 바꾸지 말고 접근 한계를 기록한다.
3. 실제 후보와 연결되는 검색어를 열어 상위 게시물 5~10개 이하의 제목·URL·화면 순위를 참고한다. 읽지 않은 글의 내용·표현·사진은 수집하거나 재사용하지 않는다. 후보와 무관한 순위는 채택하지 않는다.
4. 관찰 결과를 아래 JSON으로 전달한다. 카테고리·목록 종류·화면 기준일·확인 시각·순위·출처가 필수다. 수치를 추정하지 않는다.
5. 코드가 유효성/최신성을 확인한 뒤 **후보 예약과 유료 조사·작성 이전**에 실제 입력끼리만 비교한다. 일치하는 기사 근거가 있고 최근 제목 중복 위험이 낮은 후보를 같은 카테고리/편집 우선순위 안에서 우선한다. 서로 다른 검색어의 순위 숫자를 정밀한 점수로 합산하지 않는다.
6. `creator-trend-selection.json`에 비교 결과, 선택 전 순서, 미확인 상태를 남긴다. 선택된 입력의 `provenance.creator_trends`가 원고·심사·암호화 인계까지 따라간다. 준비 결과/알림에도 해당 상태가 표시된다.

사용자 지정 주제(예: 2026-10-09 알테오젠 예정 촉매)는 트렌드 때문에 교체하지 않는다. 해당 금요일 자료·수동 편집 지정이 실제 준비 경로에 반영됐는지는 별도 확인 대상이며 이 기능이 새 예약이나 적격 KIS 원본을 만들어 주지 않는다.

## 현재 런타임으로 전달하는 방법

**09:00 GitHub Actions는 로그인된 Work 또는 dot 브라우저를 공유하지 않는다. 이 PR은 무인 로그인 수집을 추가하지 않는다.** 실제 수집은 다음의 한정된 수동/Work 단계다.

### 활성 09:00 API 준비 경로

1. 승인된 수동/Work 작업에서 위 화면을 읽고 `config/creator-trends.example.json` 형식의 관찰 JSON을 작성한다. 예제는 `enabled: false`이고 실제 근거로 사용되지 않는다. 관찰한 값으로 바꾸고 `enabled: true`로 바꾼다.
2. 준비 시작 **전에** 저장소의 Actions 변수 `BLOG_CREATOR_TRENDS_JSON`에 검증된 JSON을 전달한다. 새 로그인·자격 증명은 필요 없다. 이 변수는 비밀 저장소가 아니므로 공개 검색어·게시물 제목·공개 URL·목록 기준일/순위만 넣는다. 개인 트래픽·수익·가족 정보·계정 쿠키·토큰·원문 본문·사진은 넣지 않는다. 변수 입력/갱신은 승인된 운영자가 수행한다.
3. 기존 `blog-prepare.yml`이 그 값을 환경 변수로 전달하고 `run_daily → rank_candidates → consult`가 읽는다. 파일만 Work PC에 저장하는 것은 Actions 전달이 아니다. **09:15 저장 또는 10:15/11:15 점검에서 읽은 결과는 이미 끝난 당일 09:00 주제 선정에 소급 적용되지 않는다.** 다음 준비 전에 전달하면, 당시 최신성 기준을 만족할 때만 사용한다.
4. 자연 예약 실행의 결과에서 `creator_trends_status`와 암호화 인계의 선택 기록을 확인한다. 이 작업만을 위해 유료 준비를 수동 실행하거나 새 반복 일정을 만들지 않는다.

변수는 아직 실계정에 등록·갱신하지 않았다. PR 병합과 첫 관찰 스냅샷 전달/자연 실행 확인 전에는 자동 반영 완료로 말하지 않는다. 운영 중 수동/Work 갱신이 없으면 36시간 뒤 만료된다.

### 로컬 실행/검증 경로

`blogbot import-creator-trends --file /private/observed-trends.json`

명령은 검증 후 현재 `BLOG_DATA_DIR`의 비공개 상태 파일에만 기록한다. 네이버·모델·생성·저장·예약을 호출하지 않는다. 같은 환경에서 실행한 다음 준비가 사용한다. **로컬 import만으로 GitHub Actions 상태를 갱신하지 않는다.** 활성 API 경로에는 위 변수 전달이 필요하다.

## 캐시와 실패 시 동작

- 확인 시각은 시간대가 필요하며 미래 시각은 무효다. 확인 후 최대 **36시간**, 화면 데이터 날짜는 당일 대비 최대 **3일 전**까지 인정한다. 당일 데이터가 없다는 이유로 날짜를 오늘로 고치지 않는다.
- 유효한 스냅샷과 선택 기록은 기존 암호화 체크포인트에 포함된다. 환경 변수가 비어 있으면 유효한 캐시를 재사용한다. 새 값이 잘못됐으면 오래된 값으로 조용히 대체하지 않는다.
- `UNAVAILABLE`, `INVALID`, `WRONG_CHANNEL`, `EXPIRED`, `FUTURE_CAPTURE`, `EXPIRED_DATA`, `CATEGORY_UNAVAILABLE`, `NO_RELEVANT_MATCH`를 명시한다. 검색어 목록만 있으면 `KEYWORDS_ONLY`, 관련 게시물까지 있으면 `CONSULTED`다.
- 근거가 없거나 관련성이 없으면 기존 입력·우선순위를 유지한다. 트렌드 미확인만으로 새 유료 조사/재작성·이미지 생성·자동 재시도·전체 작업 차단을 추가하지 않는다. 실제 질문이나 필수 1차 근거가 없으면 기존 보류 규칙이 그대로 적용된다.
- 최근 DB 제목과 기존 공개 제목 이력을 비교한다. 제목 유사성은 위험 표시이고 본문 중복 확정이 아니다. 최종 원고의 기존 중복 심사는 유지한다.
- 이미 비용이 발생한 요청은 최초 선택 근거를 재사용한다. 새 트렌드가 이전 글의 캐시를 바꾸거나 재구매시키지 않는다. 과거 원고·복구 예산·저장 불확실 상태를 초기화하지 않는다.

## 입력 경계

최대 UTF-8 40KB, 최대 6개 그룹, 그룹당 실제 관찰 항목 10개. 등록된 블로그 ID가 맞아야 한다. 출처는 관찰된 Creator Advisor URL, 기사는 네이버 블로그의 개별 글 URL만 허용한다. 현재 확인된 화면은 유입 순위만 제공하므로 `views`에 숫자를 넣으면 거절한다. 지원되지 않는 private API, 쿠키 추출, 로그인 우회, 유료 API 연결은 없다.

## 지속 운영 활성화 제안 (아직 미실행)

**권장: 기존 09:15 Work 작업에 다음날 근거 수집을 추가**한다. 준비·저장 지시와 10:15/11:15 점검 시각은 바꾸지 않는다. 09:15 작업의 마지막 독립 단계에서 다음날 편성에 맞는 관찰을 최대 7분 동안 하고, 승인된 단일 변수만 갱신한다. 다음날 09:00 사용 시 확인 후 약 23시간45분이 지나므로 위 최신성 한도 안에 든다. 직전 날 데이터까지 제공되면 다음 준비 시 데이터 나이는 보통 2일이다. **화요일 작업에서는 수요일 운동, 목요일에는 금요일 투자, 나머지는 다음날 육아**를 준비한다. 수집 실패를 이유로 당일 저장·복구를 재실행하지 않는다.

더 최신인 당일 자료가 반드시 필요하면 별도 08:40 KST 수집 작업을 제안할 수 있지만, 새 반복 일정과 운영 비용이 생기므로 현재는 만들지 않는다. 시작 시각이 08:40이어도 08:55까지 전달하지 못하면 당일 반영을 보장할 수 없다.

PR 코드만 병합되면 미확인 상태를 정확히 기록하는 입력 경로가 켜질 뿐이다. 첫 전달과 자연 실행 검증이 끝날 때까지 매일 자동 참고가 운영 중이라고 표현하지 않는다.

선택 기록 저장 자체가 실패하면 `CREATOR_TRENDS_RECORD_UNAVAILABLE`을 실행 로그에 남긴다. 새 후보에는 저장하지 못한 참고 입력을 붙이지 않으며 이미 유료 시도한 요청의 저장된 근거는 보존한다. 이전 비교 기록이 있지만 아직 시도하지 않은 요청은 그 기록을 안전하게 교체/제거할 수 있을 때까지 해당 ID만 보류한다. 보고서 파일만 실패한 경우에는 내구성 있는 선택 기록을 유지한 채 계속한다.
