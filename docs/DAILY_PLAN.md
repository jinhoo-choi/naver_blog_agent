## 입력과 금요일 투자 원본

요일표는 주제 목록이 아닙니다. **14개 주제를 미리 생성하거나 입력한 것으로 간주하지 않습니다.**

추가하지 않습니다. 당일 카테고리에 맞는 실제 질문·자료가 없으면 `PLANNED_INPUT_REQUIRED`로

육아일에는 일반 `article` 또는 실제 자료를 제공받은 `ai_tutorial`을 선택할 수 있습니다.
일반 육아 질문을 자동으로 AI 튜토리얼로 바꾸지 않습니다. ChatGPT 대화를 상시 자동 수집하지 않습니다.

생략하고 `EDITORIAL_SLOT_RESERVED`를 보고합니다. 새 입력이나 가짜 request_id를 만들지 않습니다.

날짜를 10월 5일로 옮기거나 API가 준비·저장한 것으로 표시하지 않습니다. 다음 날짜부터는
`weekly-4111-v1` 요일 계획을 적용하며 일괄 중단이나 다른 글 자동 채우기가 아닙니다.

리포트·공시·다른 종목·옛 정책으로 빈 슬롯을 채우지 않습니다. 다른 요일과 과거 운영의 문턱은 바꾸지 않습니다.

두 시계를 따로 확인합니다. 먼저 `community.snapshot_ready_hour=7`에 따라 **당일 07:00 KST 이후의
최신 export**가 준비됐는지 확인합니다. 그다음 커밋에 고정한 제한된 이력에서 원본 발표·새 단계의

가격·시세·수급 데이터는 기존 D-1/D0를 유지하며 5일 허용을 적용하지 않습니다.
원본 ID·커밋·원문 URL·해시와 중복/철회 여부를 보존합니다. 더 최신의 탈락·철회 자료를 건너뛰어
과거 통과본을 되살리지 않습니다. 원본 저장소는 읽기만 하며 수정·실행·발송하지 않습니다.

원본을 통과한 뒤에만 비공개 정책 근거를 연결합니다. 실제 새 변화, 기업의 공식 참여/기존 사업/사업 관련성,

공식 근거로 검증합니다. 출처 목록·JSON 등록은 사실 승인이나 원문 열람 증거가 아닙니다.

근거 등록·암호화 운반·보류 조건은 [WEEKLY_POLICY](WEEKLY_POLICY.md), [INPUTS](INPUTS.md)를 따릅니다.

## 화요일 유래와 다른 요일의 심화 기준

화요일 `origins`는 [ORIGINS_EDITORIAL](ORIGINS_EDITORIAL.md)을 따릅니다. 첫 1~2문장에 답하는 약 350~600자의 짧은 본문, 별도 연재 소개, 신뢰할 수 있는 유래 출처와 제공·승인된 썸네일만 사용합니다. 5장 생성·실제 이미지 2장·링크카드·재사용 자료·실천 단계 등 심화 템플릿의 수량 문턱은 유래에 적용하지 않습니다.

나머지 정기 글에는 주말에만 적용하던 깊이와 실제 증거 기준을 적용합니다. 글의 길이나 획일적인
목차보다 **질문에 대한 답, 확인한 근거, 실천 단계·조건, 재사용 체크리스트/자료,
공식 직접 링크, 확인된 한계**를 우선합니다. 세부 기준은
[BLOG_SETUP](BLOG_SETUP.md#매일-심화-콘텐츠), [CONTENT_QUALITY](CONTENT_QUALITY.md)를 따릅니다.

- 기존 심화 저장 기준인 확인 가능한 실제 이미지 2장 이상, 공식 직접 링크카드
  1개 이상, 재사용 자료 1개를 유지합니다. 실제 캡처 3~5장은 목표이며 같은 화면을
  반복하지 않습니다. 출처와 재사용 권한을 확인하고 개인정보를 가립니다.
- 육아는 적용 조건·관찰/중단 신호, 운동은 자세·수행·안전장치, 투자는 사건과 원문의
  관계·남은 조건/일정, 가족-AI는 실제 설정·입력·결과·재현 순서를 확인합니다.
  같은 소제목이나 영상·프롬프트를 모든 글에 강제하지 않습니다.
- 텍스트 심사 때 아직 촬영되지 않은 캡처 때문에 유료 재작성을 반복하지 않습니다.
  저장 전 실물 자료가 부족하면 보류합니다. UI·문서·결과를 AI 이미지로 위조하지 않습니다.
- 기존 모델, 글당 생성 이미지 수(육아·운동 5장, 투자 3장/본문 2,500자 이상 4장),
  동시 호출 수, 비용/재시도 한도, 24/30·정확성/안전성 각각 4/5 기준을 바꾸지 않습니다.
  실제 자료와 중복되는 보조 삽화는 생략할 수 있습니다. 새 유료 영상·추가 이미지
  생성으로 심화 요건을 메우지 않습니다. 최종 발행은 사용자가 직접 합니다.

## 실행·복구·당일 합산

- 기존 **09:00 준비 → 09:15 저장 → 10:15 복구 점검(KST)** 시각을 유지합니다.
  준비·저장·복구는 같은 당일 1편을 완성하는 단계이며 각각 1편이 아닙니다.
  시작 시각은 완료 보장이 아닙니다. 추가 예약을 만들거나 기존 복구 예산을 늘리지 않습니다.
- API 후보 예약, Work 임시저장, 수동/재실행, 복구를 합쳐 당일 1편 한도를 확인합니다.
  Work의 당일 검증된 전체 receipts와 실제 저장/발행 목록을 대조합니다.
  새 receipt에는 실제 저장일(진행/불확실 상태는 저장 시도일) `day="YYYY-MM-DD"`를 남깁니다.
  기존 기록의 명시적 `day`, `saved_display="YYYY.MM.DD HH:MM"`와 명시적 `saved_display_timezone`, 시간대가
  있는 `saved_at`/`draft_saved_at`도 실제 저장일 증거로 사용할 수 있습니다. 여러 증거의
  날짜가 다르거나 날짜 증거가 없으면 보류합니다. 원고 `as_of_date`나 전체 목록의
  `verified_date`에서 저장일을 추정하지 않습니다. `save_receipts`에는 실제 저장일을
  원래 생성 시도일과 별도로 보존하므로 과거 원고라도 오늘 저장됐다면 오늘 한도를 소비합니다.
  `SAVING`·`SAVE_UNCERTAIN`·`SAVED_NAVER`·`PUBLISHED`는 중복 저장에서 제외하고,
  미확인 저장은 목록 확인 전 재시도하지 않습니다. 확인 실패를 빈 이력으로 취급하지 않습니다.
- 당일 복구는 원래 `request_id`와 기준일, 예약·유료 호출·이미지 이력 및 기존 한도를
  재사용합니다. 당일의 유효 계획과 일치하는 작업만 자동 진행합니다. 요청·원고의
  provenance와 `ready.json`의 `daily_plan`을 대조합니다. 새 ID, 날짜 변경, 파일 삭제,
  한도 초기화로 재생성하지 않습니다.
- **과거 날짜의 유료 원고·이미지·미완료 상태는 그대로 보존하고 보류합니다.**

## 측정과 실제 전환 확인

10월 5~18일에는 날짜·요일·실제 입력·카테고리/하위유형·준비/저장/발행 여부·보류 사유와
기록된 API 사용량을 비교합니다. 제목·본문·개인 자료는 비공개 기록에 둡니다.
기존 발행 후 D0~D2, D0~D6, D0~D27 분석은 해당 구간이 지난 글만 확인합니다.
미제공 지표를 0으로 채우거나 2주만으로 검색 순위·수익 개선을 확정하지 않습니다.

실제 전환 완료는 아래를 각각 확인한 뒤에만 보고합니다.

1. 승인된 코드가 실제 실행 버전에 배포되어 10월 5일 구계획 보존, 10월 6일 이후 새 요일·하루1편 제한과 선택적 AI 하위유형을 사용하는지 확인
2. 외부 Work 저장·복구 지시문에 날짜별 계획, 당일 합산 1편, 과거 원고 보류, 유래 전용 짧은 글 예외를 반영하고 다시 읽어 확인
3. 기존 외부 예약 시각과 권한을 그대로 확인하며 중복 스케줄을 활성화하지 않음
4. 실제 당일 입력과 receipts, 승인 원고·실물 자료를 확인한 첫 준비·저장 결과 검증
5. 이름의 유래 카테고리 9와 실비김치의 10월 5일 실제 저장 증거를 보존하며 10월 6일 예약과 구분. 서식·대표 설정 및 외부 지침의 개별 확인 범위를 저장 성공만으로 확대하지 않음

기존 `daily-deep-511-v1`의 원격 코드·Work 지시문 반영과 10월 5일 자연 준비의 예약 건너뜀까지 확인했습니다. 새 `weekly-4111-v1`의 코드 반영·외부 지침 등록·실계정 저장은 각각 별도로 확인해야 합니다.
실제 모델 입력의 프롬프트까지 같은 계획인지 확인하며 불일치는 `CONFIG_SYNC_PENDING`으로
보류합니다. 10월 5일 09:00의 예약 건너뜀은 생성·저장 성공 사례가 아니며, 같은 날 19:17 KST의 실비김치 수동 저장은 별도 증거입니다. 19건의 실제 저장일 이관은 다음
정상 비예약 준비에서 실행되며, 운영 DB 반영과 첫 무인 저장 완료는 실제 증거로 확인합니다.
외부 Work에 접근하지 못하면 접근 미확인과 구성 불일치를 구별해 보고합니다.

### 저장일 증거 이관 주의

시간대가 표시되지 않은 UI 시각을 KST로 추정하지 않습니다. `saved_display`만 있다면
확인된 `saved_display_timezone`(예: 실제로 확인한 `Asia/Seoul`) 또는 시간대가 있는
실제 `saved_at`을 확보합니다. 독립적으로 확인한 실제 KST 저장일 `day`는 사용할 수
있으며, 이때 시간대 없는 표시 문자열은 날짜 추론에 쓰지 않습니다.

`attempts.day`는 생성 시도일이며 저장일이 아닙니다. 검증된 `save_receipts`의 실제
저장일을 우선하며, 원고 작성일·시간대 없는 DB 시각·상태 해결 시각으로 대신하지
않습니다. 과거 `SAVED_NAVER` 기록에 실제 날짜 증거가 없으면
`save_date_reconciliation_required`로 보류하고 기존 기록과 과금 한도를 보존합니다.
외부 Work 지시문 및 이 이관을 확인하기 전에는 새 운영을 활성화했다고 보고하지 않습니다.

수동 `resolve --outcome saved`에는 검증한 실제 `--saved-at`(시간대 포함) 또는
`--saved-day`(실제 KST 저장일)가 필요합니다. 위 명령의 시각은 형식 예시이므로
그대로 사용하지 말고 확인한 값으로 바꿉니다. 오늘 해결했다고 오늘 저장한 것으로
기록하지 않습니다. 즉시 성공이 확인된 자동 저장만 현재의 실제 저장 완료 시각을 씁니다.
