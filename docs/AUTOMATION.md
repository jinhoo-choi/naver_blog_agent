# 승인된 작성·발행·교류 운영

2026-10-10 소유자가 진단 개선안의 구현, 작성·발행·교류 자동화, 단계별 검수와 코드 병합을 승인했습니다. 이 문서가 **실행 권한·시간·완료 판정**의 현재 기준입니다. 과거 문서의 사용자 직접 발행 전용·구 3편·10회 한시 교류 지시는 대체합니다. 편성·입력은 [DAILY_PLAN](DAILY_PLAN.md), 문체는 [CONTENT_QUALITY](CONTENT_QUALITY.md), 실제 값은 `config/blog.toml`을 따릅니다. 10/10·11 입력 홀드와 과거 수동 원고는 자동 해제하지 않습니다.

## 실행자와 시간 (Asia/Seoul)

| 단계 | 실행자 | 시각 | 책임 |
|---|---|---|---|
| 작성·심사·이미지 | 기존 cron-job.org → Blog API Prepare | 09:00 | 실제 당일 입력 1편, 근거·기계검수·독립 심사, 암호화 인계 |
| 검수·저장·발행 | 기존 Work 저장 예약 1개 | 09:15, 11:15 | 같은 원고의 주 실행·누락 보완. 이미 발행됐으면 읽기만 하고 종료 |
| 트렌드·교류·실적 | 기존 Work 교류 예약 1개 | 20:05 | 다음 준비용 공개 트렌드, 미답글→기존 이웃→신규 이웃, 완료 실적 |

09:15에 준비가 진행 중이면 새 준비를 실행하거나 기다리며 반복 조회하지 않습니다. 11:15에 같은 실행 결과를 확인합니다. 기존 별도 10:15/11:15 점검, 구 3편 저장, 구 9/28 캠페인은 비활성 유지합니다. 하나의 작업에서 다른 예약을 `run_now`로 호출하지 않습니다. 예약의 실제 등록·활성·다음 시각은 도구 응답으로 따로 확인합니다. Work 모델 필드가 제공되지 않으면 Sol 설정을 완료했다고 주장하지 않습니다.

## 비공개 원장과 중복 방지

기존 비공개 `naver-blog-performance.md`를 이어 씁니다. 첫 실행에서 현재 지표·원고별 상태·교류 작업을 상단에 정리하고 과거 기록은 보존합니다. 상대 계정·댓글 문안·개인 통계·원고·키는 공개 Git에 올리지 않습니다.

- 매 실행 최신 원장과 실제 네이버 목록을 대조합니다. 접근 실패·모호한 이력은 0건/빈 배열로 간주하지 않습니다.
- 원고별 원래 `request_id`, 작성일, 실제 저장일, 발행일, run/artifact 식별자, 본문·이미지 해시, 단계·사유를 구분합니다. 저장과 발행은 같은 원고의 단계이며 2편으로 세지 않습니다.
- 공개 직전 수동·자동 당일 발행 합산 1편을 확인합니다. API 준비/저장 한도도 유지하며 수동 발행으로 한도가 찼으면 새 글을 저장·발행하지 않습니다.
- 제목만 비슷한 새 ID를 만들지 않습니다. 원본 ID·제목·핵심 질문과 기존 공개 URL을 함께 확인합니다. 같은 검색 의도는 새 글보다 기존 글의 후속 질문을 제안하되 기존 공개 글의 편집·삭제·합치기는 자동 수행하지 않습니다.
- 브라우저 작업 시작 전 실행 ID·작업·시각을 원장에 기록합니다. 다른 실행이 진행 중이거나 쓰기 결과가 미확인이면 `DEFERRED_BROWSER_BUSY`/불확실 상태로 종료합니다. 종료 때 자신의 작업만 해제하며 오래된 잠금도 실제 상태 대조 없이 지우지 않습니다.
- 원장 저장이 실패하면 다음 외부 쓰기를 하지 않습니다. 파일 전체를 오래된 사본으로 덮어쓰지 않도록 최신 버전에서 갱신합니다.
- 과거 AI 돌봄 수동 원고의 `SAVE_UNCERTAIN`과 삭제 미확인은 실제 목록으로 해소하기 전까지 유지합니다. 기존 편집기·제목 유사 초안을 새 자동화 대상으로 삼거나 새 ID로 복제하지 않습니다.

## 작성과 독립 검수

1. 당일 계획·입력·수동 홀드·한도를 먼저 확인합니다. 실제 질문이나 적격 정책 근거가 없으면 `PLANNED_INPUT_REQUIRED`로 보고합니다. 편성표나 트렌드로 질문·경험을 창작하지 않습니다.
2. 확인한 1차 출처로 작성합니다. 벤치마크는 구성 참고에만 쓰고 문장을 복제하지 않습니다. 도입의 답, 쉬운 습니다체, 짧은 문단, 중복 없는 본문·캡션을 확인합니다. 최소 1,800자·대제목 4개를 채우지 않습니다.
3. 기존 기계검수 → 독립 원문 대조·심사(24/30, 정확성·안전성 각각 4/5) → 최대 1회 수정 경로를 재사용합니다. 생성 이미지 수는 기존 설정의 상한 안에서 고유 설명 구역에 맞춥니다. 기존 유료 캐시·이미지 계획·재시도 한도를 초기화하지 않습니다.
4. 후기·AI 튜토리얼은 실제 제공 사진·화면·결과를 확인합니다. 일반 정보 글에 실사진 2장·카드 1개·체크리스트를 일률 강제하지 않습니다. 근거·주장에 필요한 자료가 없으면 분량을 채우지 않고 해당 글을 보류합니다.
5. Work는 승인된 최종 본문·이미지 실물을 대조합니다. 의료 자세, 통계·투자 수치와 사건 날짜, 출처, 공개 승인 범위, 개인정보, 모바일 문단·표·구분선·대표 이미지·태그를 확인합니다. 새 사실을 추가하는 수정은 심사 없이 발행하지 않습니다. 이전 성과에서 고른 편집 개선 1개만 근거 범위 안에서 적용합니다.

## 인계 실행 환경과 영수증 이관

연결된 GitHub 도구로 당일 `blog-state-<run_id>-<attempt>` ZIP의 `bundle.enc`를 받습니다. 기존 비공개 런타임 키 파일의 `fernet_key`는 `BLOG_BUNDLE_KEY` 환경변수로만 전달하고 출력·로그·Git에 넣지 않습니다. 파일 식별자는 비공개 예약 지침을 따르며 원장 키와 코드 파일을 혼동하지 않습니다.

`unpack --destination`은 다음 명령의 환경변수를 바꾸지 않습니다. 아래 경로들을 같은 복호화 디렉터리로 명시하여 import/claim이 다른 DB를 읽지 않게 합니다. 경로는 예시이며 실제 비공개 작업 경로로 지정합니다.

```sh
work_bundle_dir=/absolute/private/restored-bundle
export BLOG_DATA_DIR="$work_bundle_dir"
export BLOG_DB_PATH="$work_bundle_dir/blog.db"
export BLOG_ARTIFACT_DIR="$work_bundle_dir/drafts"
export BLOG_INBOX_DIR="$work_bundle_dir/inbox"
python -m blogbot.cloud unpack --file /absolute/private/bundle.enc --destination "$work_bundle_dir" --receipts /absolute/private/receipts.json
blogbot import-work-receipts --file /absolute/private/receipts.json
```

외부 영수증은 `verified_date`(실제 오늘 확인일), `records`에 `request_id/category/day/status`를 포함합니다. `category`는 원래 입력/원고와 실제 카테고리를 대조하며 추정하지 않습니다. 기존 `config/manual-saves.json`은 과거 저장 증거로 재사용하되 날짜를 오늘로 옮기거나 발행 완료로 승격하지 않습니다. 기존 PUBLISHED는 실제 공개 URL·글 ID·발행시각을 보강합니다. 증거가 빠진 과거 기록을 삭제하거나 SAVED_NAVER로 낮춰 검사를 통과하지 않습니다. 확보할 수 없는 증거는 구체적 보류 사유로 보고합니다.

## 저장과 공개 발행

API의 `success`, 입력 대기, `TEXT_APPROVED`, `APPROVED`를 네이버 저장/발행과 구분합니다. GitHub 실행기는 네이버 공개 버튼을 누르지 않습니다. 공개 발행은 이 문서를 읽은 Work 실행자만 담당합니다.

1. 당일 `ready.json`의 계획·기준일·request_id·검수·파일 해시와 실제 원장을 대조합니다. `posts`는 신규 저장 후보, `publication_ready`는 저장 증거가 있는 같은 당일 글의 발행 후보입니다. 둘을 새 글 2편으로 세거나 이미 저장된 글을 다시 저장하지 않습니다. 복호화·인계는 [OPERATIONS](OPERATIONS.md)의 기존 경로입니다. 수동 초안·과거 날짜 원고·입력/사용자 확인 홀드는 자동 발행 대상이 아닙니다.
2. 저장 전 본문과 이미지·카테고리를 확인하고 원장에 `SAVING`을 먼저 보존합니다. 저장 완료 표시·목록의 제목/시각을 확인하면 `SAVED_NAVER`. 결과 불명은 `SAVE_UNCERTAIN`입니다. 저장본을 검수 목적으로 다시 열지는 않습니다.
3. 같은 실행에서 공개 직전 제목·본문·대표 이미지·카테고리·공개범위를 확인합니다. 이미 저장된 같은 당일 원고를 보완 실행에서 발행하려면 정확한 대상이 확인된 경우에만 열고 새 복제본을 만들지 않습니다.
4. 최신 외부 영수증을 가져온 비공개 DB에서 `blogbot claim-publication --request-id <원래 ID>`를 실행하고 `PUBLICATION_CLAIMED`일 때만 진행합니다. 이 명령은 당일 ready 원고·심사·파일·계획·한도·실제 저장 상태를 대조하며 네이버를 클릭하지 않습니다. 반환된 `PUBLISHING`과 시간대 있는 `publish_attempted_at`을 비공개 원장에 저장한 뒤 공개 버튼을 한 번 누릅니다. 클릭 결과가 모호하면 `PUBLISH_UNCERTAIN`으로 남기고 재클릭하지 않습니다. 다음 실행은 공개 목록 대조부터 하며 미발행이 확인됐더라도 이전 시도 이력을 삭제하지 않습니다.
5. 실제 공개 페이지의 제목·본문·소유 블로그·글 ID·공개 URL·발행시각을 확인한 뒤에만 `PUBLISHED`, `published_url`, `post_id`, 시간대 있는 `published_at`을 기록합니다. 원래 저장일 `day`는 바꾸지 않습니다. 분까지만 표시되면 초를 창작하지 않고 `published_at_precision="minute"`과 초 00으로 관측 정밀도를 보존합니다. 시각의 시간대를 확인할 수 없으면 추정하지 않고 미확인 상태를 보존합니다. 확인한 현재 시각을 실제 발행시각으로 대신하지 않습니다.
6. 실제 외부 영수증은 `blogbot import-work-receipts --file <비공개 receipts.json>`으로 검증합니다. 필드 형식 통과 자체는 UI 성공 증거를 대신하지 않습니다. 다음 인계도 같은 원장으로 중복을 차단합니다.

불확실 발행은 우선 실제 공개 목록과 정확한 저장본을 읽기만 하여 대조합니다. 미발행이 확인되면 기존 `publish_attempted_at`을 보존하고 `PUBLICATION_NOT_PUBLISHED`와 `publication_check`를 기록합니다. 확인 정보에는 시간대 있는 `checked_at`, 소유 블로그 목록 URL `published_list_url`, 실제 확인한 `published_list_checked=true`, `draft_still_saved=true`, 비공개 증거 참조 `evidence_ref`가 필요합니다. 이 종결은 다음 날의 전체 잠금만 해소하며 같은 ID 재발행과 당일 한도 복원은 허용하지 않습니다. 미발행을 확인할 수 없으면 불확실 상태를 유지합니다.

원격 bundle 복원은 기존 목적지 DB의 저장·발행 영수증을 읽기 전용으로 확인하고 임시 복원 DB에 먼저 병합합니다. 충돌·손상은 기존 파일을 보존한 채 중단합니다. 새 작업 폴더에서는 과거 로컬 기록을 알 수 없으므로 매번 **모든 실제 저장·발행 시도/결과를 포함한 최신 비공개 원장**을 `--receipts`로 전달해야 합니다. `PUBLISHING` 영속화나 최신 원장 읽기에 실패하면 공개 버튼을 누르지 않습니다.

완료 보고는 제목·공개 URL·단계별 성공/보류·실제 발행수/1·계량된 사용량입니다. Work 모델·토큰·비용이 계량되지 않으면 미확인으로 표시합니다. 실패 단계와 사유를 알리고 전체 예약을 임의로 비활성화하지 않습니다. 기존 자동 복구 최대 2회·Work 실행 합산 당일 후속 recover 요청 1회·동일 ID·불확실 유료 요청 재구매 금지 경계를 유지합니다. 복구 요청도 사전에 원장에 보존하고 새 prepare/upstream 실행으로 대신하지 않습니다.

## 교류 실행과 결과 검수

매일 신규 서로이웃 신청 **최대 10명**, 기존 이웃의 최신 글 댓글·공감 **각 최대 10명**, 내 글 미답변 댓글 답글 **최대 10건**을 시작 한도로 합니다. 14일 평가 뒤에도 변경 결정 전까지 같은 한도로 계속하며 회차 종료 때문에 예약을 꺼 두지 않습니다. 수량은 채워야 할 목표가 아닙니다.

1. 미답변 댓글 → 이미 왕래한 이웃 → 관련 신규 이웃 순서입니다. 육아·가족 기록·일상 궁금증 등 공통 독자와 관련된 최신 글을 실제 읽습니다. 개인 경험·가족 반응·상대의 의도를 추측하지 않습니다.
2. 글 고유 내용 하나를 짚는 자연스러운 1~2문장으로 씁니다. 반복 칭찬·맞교류 요구·홍보 링크·억지 질문·읽지 않은 내용은 넣지 않습니다. 축하에는 짧은 감사면 충분합니다. 질문·경험 공유에는 그 내용에 답합니다.
3. 기존 이웃·신청 대기·과거 신청·결과 미확인 대상을 재신청하지 않습니다. 같은 대상의 같은 글에 댓글·공감 각 1회만 허용하며 기존 공감을 다시 눌러 취소하지 않습니다. 기존 댓글 수정·삭제·DM은 하지 않습니다.
4. 쓰기 전에 대상 ID·원문 URL·작업 종류·문안·시각·`INTENT`를 비공개 원장에 저장합니다. 화면에서 완료를 확인해야 `SUCCESS`; 실패·불확실·기존 완료·건너뜀을 구분합니다. 한 건의 기록 저장 후 다음 대상으로 넘어갑니다. 불확실한 제출은 재시도하지 않습니다.
5. 회차는 트렌드 포함 최대 45분, 브라우저 오류 누적 2회 또는 계정 경고·한도·보안 인증이면 관련 작업을 중단합니다. 적격 후보가 부족하면 미달로 종료하고 추가 회차·다른 경로로 채우지 않습니다.

신청 성공/시도, 댓글·공감·답글 성공, 실패·불확실·건너뜀만 짧게 보고합니다. 신청 제출과 상대의 수락, 누적 이웃 증가를 같은 실적으로 세지 않습니다.

## 트렌드와 성과 환류

- 교류 시작 전 최대 7분, 다음 KST 날짜의 `resolve_plan`에 해당하는 Creator Advisor 자료를 실제 읽습니다. [CREATOR_TRENDS](CREATOR_TRENDS.md)의 검증·36시간·자료 3일 조건을 지킵니다. 검증한 공개 목록 메타데이터만 `config/creator-trends.json` 한 파일에 전달합니다. 수집 실패 시 날짜를 갱신하거나 예제를 넣지 않습니다. GitHub 준비 실행의 실제 선택 기록으로 소비 여부를 확인합니다.
