# Creator Advisor를 먼저 참고하는 주제 선정 절차

구현 버전: `creator-advisor-v1` · UI 확인: 2026-10-05 KST

## 실제로 확인한 화면과 숫자의 뜻

[써누애비 Creator Advisor 트렌드](https://creator-advisor.naver.com/naver_blog/choijku/trends)에서 로그인된 화면을 확인했다.

- **검색 유입 트렌드 → 주제별 인기유입검색어**: 육아·결혼 등 주제별 검색어 목록이다. 사용자 제공 10월 4일 화면의 `▲26`, `▼3`, `new`, `-`는 조회수가 아니다. 캡처된 목록의 순서는 `keyword_inflow_order`로만 기록한다. 순위 변화 숫자를 현재 순위로 입력하지 않는다.
- **검색어 클릭 → 인기 검색어 트렌드 → 이 검색어로 유입된 게시물**: 번호가 붙은 게시물 제목과 URL이 보인다. `search_inflow_rank`로 기록한다. 개별 게시물 조회수는 보이지 않아 `views: null`이다.
- **메인 유입 트렌드 → 네이버 메인에서 많이 유입된 콘텐츠**: 전체 주제의 유입 순서다. `main_inflow_rank`이며 전체 인기 연예 글을 육아 주제로 자동 선택하지 않는다.
- **주제별 트렌드 → 조회수**는 주제 단위 차트다. 이를 개별 글 조회수로 쓰지 않는다.
- 조회 당시 메인 날짜는 10월 3일, 열린 검색어 상세 화면은 10월 2일을 표시했다. URL의 날짜나 오늘 날짜를 대신 넣지 말고 **각 실제 목록 위에 표시된 날짜**와 최종 관찰 URL을 함께 보존한다. 날짜가 서로 다른 화면은 별도 그룹으로 기록한다.

이 순위는 검색노출 순위·검색량·저경쟁·상위노출 보장이나 사실 검증의 증거가 아니다.

## 현재 운영 순서

실행 일정·발행·교류 권한과 공통 중단 조건은 [AUTOMATION.md](AUTOMATION.md)를 따른다. 이 문서의 과거 요일표나 Actions 변수 쓰기 제안을 별도 실행 지시로 사용하지 않는다.

1. 매일 20:05 KST 회차의 교류 후 **다음 KST 날짜의 유효 편성**을 `config/blog.toml`과 `docs/DAILY_PLAN.md`로 확인한다. 실제 사용자 질문·소유자 지정 주제·수동 홀드가 우선이다. 입력 없음·수동 홀드는 UI 수집을 생략하며 새 주제·질문을 만들지 않는다. 낮 회차와 별도 수동 교류에서는 이 보조 작업을 하지 않는다.
2. 로그인된 Creator Advisor에서 써누애비/choijku 채널, 실제 표시 날짜, 다음날 카테고리의 관련 공개 검색어 목록을 직접 관찰한다. 육아는 육아·결혼, 운동은 스포츠/건강·의학, 투자·생활경제는 비즈니스·경제를 참고한다. 유래는 별도 가상 분류를 만들지 않고 실제 질문과 연결된 음식·장소 등 존재하는 UI 분류만 사용한다.
3. 실제 후보와 연결되는 검색어를 최대 5개 열고 각 목록에서 관찰한 상위 게시물 5~10개 이하의 제목·개별 URL·현재 순서·표시 자료일만 기록한다. 관련 분류·항목이 없으면 `NO_RELATED_VISIBLE_CANDIDATE`로 남기고 임의 주제로 채우지 않는다. 필터·채널 설정을 새로 저장하지 않는다.
4. 수집·검증·전달은 **남은 회차 시간 내 최대 7분, KST 날짜별 수동·정기 합산 1회**다. 시작 전에 비공개 원장에 시도와 대상일을 기록한다. 성공 여부와 무관하게 당일 시작 기록이 있으면 소진이며 같은 실행 재개도 다시 수집하지 않는다. 자료 없음·로딩 지속·채널 미설정은 미확보로 남기고 해당 보조 단계만 보류한다. 실제 브라우저 도구 예외는 교류와 동일 회차 합산 2회 중단 기준을 따른다. 계정 경고·행동 제한·로그인 상실·보안 인증도 공통 중단 조건을 따른다. 2026-10-10 17:11 수동 실행의 관찰도 당일 시도에 포함한다.
5. 아래 저장소 파일 경로로 전달하고 동일 파일을 읽어 정상 반영을 확인한다. 단순 로컬 저장·쓰기 접수는 전달 완료가 아니다. 당일 이미 끝난 09:00 준비에 소급 적용하지 않는다.
6. 다음 자연 09:00 준비의 `creator_trends_status`, `captured_at`, `snapshot_sha256`를 대조한다. 소유자 슬롯 홀드로 선정이 건너뛰어졌으면 전달 완료와 소비 미실행을 구분한다. 새 유료 prepare/recover를 실행해 확인하지 않는다.

## Actions 변수 쓰기 없이 전달하기

**GitHub Actions는 Work 브라우저를 공유하지 않는다.** Work가 직접 관찰한 목록 메타데이터를 저장소에 전달하고, runner는 checkout된 파일을 읽는다. 기존 환경 변수·암호화 상태 입력도 호환 경로로 유지한다.

### 저장소 입력: `config/creator-trends.json`

- 형식은 `config/creator-trends.example.json`의 `creator-advisor-v1`이다. 예제는 `enabled: false`인 비활성 예제로 유지한다. 관찰하지 않은 값이나 유효한 척하는 placeholder 파일을 생성하지 않는다.
- `validate_snapshot(raw)`로 검증한 **반환값을 JSON으로 직렬화**하여 기록한다. 입력 원문에 임의 필드를 붙여 그대로 커밋하지 않는다. 같은 채널인지, captured_at이 실제 관찰 시각이며 시간대를 포함하는지 확인한다. 각 그룹의 표시 자료일을 보존한다.
- 기존 GitHub 커넥터의 파일 쓰기로 `jinhoo-choi/naver_blog_agent`의 **이 단일 파일만** 갱신한다. 기존 파일 SHA/현재 버전을 대조해 동시 변경을 덮어쓰지 않는다. 새 토큰·OAuth·권한 확대나 Actions 변수 쓰기는 필요하지 않다. 커넥터의 실제 쓰기 권한이 없으면 전달 미완료로 기록한다.
- 검증에 필요한 채널·관찰시각·목록 종류·분류·검색어·출처 URL과 **공개 목록의 제목·공개 URL·순위·자료일**만 저장한다. 개인 유입 통계·수익·교류 대상 명단·댓글·가족 정보·본문·사진·쿠키·토큰은 공개 파일에 넣지 않는다. 화면 순위 변화를 현재 순위나 조회수로 변환하지 않으며 `views`는 null이다.
- 파일 갱신 뒤 같은 저장소 파일을 읽어 정규화 JSON의 SHA-256과 `captured_at`·채널·그룹 수를 대조한다. 원장에는 수집 시각·대상 준비일·실제 자료일·확인한 전달 커밋·결과를 기록한다.
- 실제 새 관찰이 없으면 기존 파일을 손대지 않는다. 이전 날짜를 오늘로 변경하거나 capture 시각만 갱신하지 않는다. 시간이 지나면 runner가 자동으로 만료 처리한다.

### 기존 호환 경로

- `BLOG_CREATOR_TRENDS_JSON`: 기존 `blog-prepare.yml`이 전달하는 환경 변수. 기존 값을 삭제하거나 다른 변수/Secrets를 변경하지 않는다. 더 최신 유효 파일을 오래된 변수 값이 가로막지 않는다.
- `BLOG_DATA_DIR/creator-trends.json`: 기존 비공개 상태 및 암호화 체크포인트. `blogbot import-creator-trends --file /private/observed-trends.json`은 검증 후 이 위치만 갱신하며 네이버·모델·생성·예약을 호출하지 않는다. 로컬 import만으로 Actions에 전달되지는 않는다.

## runner의 선택 및 최신성

1. 환경 변수, 비공개 상태 파일, 저장소 파일을 각각 독립 검증한다. `creator_advisor.channel_id`와 같은 채널이어야 한다.
2. 관찰 시각은 미래가 아니며 **36시간 이내**여야 한다. 실제 표시 자료일이 당일 대비 **0~3일 전**인 그룹이 하나 이상 있어야 한다. 모든 그룹이 오래됐으면 `EXPIRED_DATA`로 제외한다.
3. 조건을 통과한 스냅샷 중 `captured_at`이 가장 최신인 하나를 선택한다. 같은 시각이면 환경 변수 → 비공개 상태 → 저장소 파일 순서다. 선택한 원래 관찰 시각·자료일을 유지해 비공개 상태에 저장한다.
4. 잘못되거나 만료된 후보는 `CREATOR_TRENDS_SOURCE_IGNORED source=... status=...`, 실제 선택은 `CREATOR_TRENDS_SOURCE_SELECTED source=... captured_at=...`로 남긴다. 원문·개인정보는 로그에 출력하지 않는다. 유효한 다른 입력을 재사용할 수 있지만 그 재사용을 오늘 새 수집이나 새 전달 성공으로 표현하지 않는다. 유효 후보가 없으면 입력이 없을 때 `UNAVAILABLE`, 입력이 있지만 실패했을 때 첫 입력의 실패 상태를 반환한다.
5. 선택 이후에도 **각 그룹 자료일**을 다시 확인하여 오래된 그룹은 후보 비교에서 제외한다. 관련 분야나 항목이 없으면 `CATEGORY_UNAVAILABLE` 또는 `NO_RELEVANT_MATCH`다. 검색어 목록만 있으면 `KEYWORDS_ONLY`, 관련 게시물까지 있으면 `CONSULTED`다.

## 주제 선정과 비용 경계

- `run_daily → rank_candidates → consult`가 후보 예약·유료 조사·작성 전에 실행된다. 기존 실제 입력끼리만 비교하며 같은 카테고리/편집 우선순위 안에서 관련 게시물 근거와 제목 중복 위험을 참고한다. 사용자 지정 주제·적격 정책 원본·수동 홀드를 대체하지 않는다.
- 근거 부재나 관련성 부재는 기존 입력과 우선순위를 유지하는 사유다. 새 질문·유료 조사·재작성·이미지 생성·복구를 추가하지 않는다. 실제 질문·필수 1차 근거가 없으면 기존 보류 규칙을 유지한다.
- 서로 다른 검색어 순위를 합산한 정밀 점수를 만들지 않는다. 최근 DB 및 공개 제목과의 유사성은 중복 위험 표시이며 본문 중복 확정이 아니다.
- `creator-trend-selection.json`과 `creator-trend-decisions.json`에 실제 선택 근거를 기록하고 원고의 `provenance.creator_trends` 및 암호화 인계에 보존한다. 이미 유료 시도한 요청은 최초 근거를 재사용한다. 새 트렌드가 기존 캐시·원고·복구 예산·저장 상태를 초기화하지 않는다.
- 선택 기록 저장 실패는 `CREATOR_TRENDS_RECORD_UNAVAILABLE`로 보고한다. 새 후보에 미저장 근거를 붙이지 않으며 이미 유료 시도한 요청의 근거는 보존한다. 이전 미시도 후보의 기록을 안전하게 교체하지 못하면 해당 ID만 보류한다. 선택 보고서만 실패하면 내구성 있는 결정 기록으로 계속한다.

## 입력 경계와 운영 확인

최대 UTF-8 40KB, 최대 6개 그룹, 그룹당 실제 관찰 10개다. 출처는 관찰된 Creator Advisor URL, 게시물은 네이버 블로그의 개별 공개 URL만 허용한다. `views`의 숫자는 거절한다. private API·쿠키 추출·로그인 우회·추가 유료 수집은 없다.

코드 병합과 예약 설정은 입력 경로의 준비다. **첫 실제 관찰 → 파일 전달 확인 → 다음 자연 준비의 동일 snapshot 소비**까지 확인한 뒤에만 자동 참고가 실제 운영됐다고 보고한다. 새 스냅샷이 없거나 입력 홀드로 선정이 실행되지 않으면 각각의 상태를 그대로 보고한다.
