# 금요일 새 정책 분석

기준일: 2026-10-06 KST · 계약 버전: `weekly-policy-v1`

금요일 투자 슬롯의 주제는 **최근 5 calendar days, D-4~D0에 실제로 새로 발표됐거나 공식 새 단계가 생긴 정책 1건**입니다. 새 변화, 확인된 기업 관계의 수준, 앞으로 남은 일정·조건을 설명합니다. 예를 들어 2026-10-09의 창은 2026-10-05~09입니다. 거래일 5일이나 최근 120시간으로 바꾸지 않습니다.

이 기준은 `daily_plan.investment_mode="weekly-policy-v1"`인 금요일에만 적용합니다. 다른 요일, 과거 실행·유료 원고·저장 영수증, 준비·수동·저장·복구 합산 하루 1편, 기존 모델·이미지·검수·재시도 예산은 그대로입니다. `research`·`disclosure`, 관심 종목, 오래된 정책, 일반 투자 질문으로 빈 슬롯을 대체하지 않습니다.

## 두 개의 시간 기준

1. **최신 export 준비**: KIS `data/posts_latest.json`의 가장 최신 커밋을 고정해 읽고, 그 시각이 실제 당일 07:00 KST 이후인지 확인합니다. 미래 시각·날짜/시간대 미확인·어제 export는 준비 완료가 아닙니다. `community.snapshot_ready_hour=7`을 유지합니다.
2. **정책의 새 변화**: 제한된 커밋 이력의 원본에서 실제 발표 또는 공식 새 단계의 날짜가 D-4~D0인지 확인합니다. 대응하는 공식 원문의 발행일·날짜 인용과 맞아야 합니다. 수집일·커밋일·파일 갱신일·재게시일·미래 시행/행사일은 새 발표일을 대신하지 않습니다.

가격·주가·시세·수급의 실제 데이터 날짜는 기존 **D-1/D0**를 유지합니다. 정책 5일 창이나 배경 자료 예외로 오래된 시장 데이터를 통과시키지 않습니다. 시장 수치가 있는 원본은 `market_as_of_date`와 원문 날짜를 별도로 확인하며, 단순 시황 요약으로 글을 만들지 않습니다.

원본의 기존 6개 점수, `fatal=[]`, 정확성·준법·적합성 및 `min_score` 문턱은 낮추지 않습니다. 블로그 최종 심사도 24/30 이상, 정확성·안전성 각각 4/5 이상과 기존 blocking issues를 유지합니다. 적격 원본이나 검증 가능한 근거가 없으면 보류합니다.

## 읽기 전용 이력과 중복·철회

- 기존 GitHub 읽기 경로에서 `posts_latest.json`의 제한된 커밋 이력만 확인합니다. 기본 `max_history_exports=20`이며 무한 페이지 조회·원본 봇 실행·수정·발송은 하지 않습니다.
- 각 원본의 실제 커밋, 원본 ID, 출처 URL, 원본 해시, 실제 자료일과 최신 준비 확인 export를 구분해 보존합니다.
- 최신 버전부터 같은 원본 ID/출처를 대조합니다. 최신 탈락·철회·비적격 버전을 건너뛰어 예전 통과본을 되살리지 않습니다. 뒤의 일일 export에서 단순히 사라진 것은 명시적 철회와 구분합니다.
- 요청 ID는 기존 repository+원본 ID 기반 `community-…`를 유지합니다. 공식 사건 URL+실제 새 변화 날짜의 별도 event key로 같은 사건이 다른 원본 ID로 재게시돼도 중복 유료 시도를 막습니다. URL의 중요한 문서 쿼리 값을 버리지 않습니다.
- 재시도는 같은 ID·기준일·유효 계획과 기존 예약/유료 호출 이력을 사용합니다. 새 ID, 날짜 변경, DB/파일 삭제, 예산 초기화로 다시 생성하지 않습니다.

## 비공개 근거 계약

근거 묶음은 **이미 존재하는 적격 KIS 원본에만 연결하는 보충 자료**입니다. 이것만 등록해 투자 후보·원고·승인을 만들 수 없습니다. 일반 `enqueue`, 날짜 지정 질문, 직접 `ContentRequest` 주입으로 KIS 원본 심사·최신성·중복 검사를 우회하지 않습니다.

최상위 필드는 다음과 같습니다. 날짜는 실제 확인한 `YYYY-MM-DD`이며 예시 날짜·URL·해시를 실제 근거로 쓰지 않습니다.

| 필드 | 내용 |
|---|---|
| `version` | 정확히 `weekly-policy-v1` |
| `source` | 원본 결합: `repository`, 40자리 커밋 `commit`, `record_id`, 원본 `url`, 64자리 `record_sha256` |
| `event` | `date`, `novelty`, `stage`, 실제 새 변화 `change`, 원본 facts의 정확한 `export_excerpt`, 공식 `source` |
| `background_sources` | 종전 정책/과거 사업의 공식 source 배열. 각 항목은 해당 과거 날짜를 포함한 정확한 원본 `export_excerpt`도 필요 |
| `company_links` | 기업 이름 `company`, 관계 수준 `relationship`, 근거가 뒷받침하는 `claim`, 공식 `source` |
| `milestones` | 공식 날짜 또는 `null`인 `date`, 충족 조건/미정 사유 `condition`, 공식 `source` |

여기서 원본 결합용 최상위 `source`와, 주장별 공식 자료 `source`는 서로 다른 구조입니다. 주장별 공식 source에는 `url`, `published_date`, 정확한 본문 `excerpt`, 발행일을 보여 주는 정확한 `date_excerpt`가 필요합니다. 원본 결합은 repository·commit·record_id·url·record_sha256이 모두 일치해야 하며 일부 일치나 같은 사이트라는 이유로 다른 문서를 연결하지 않습니다.

`record_sha256`은 해당 커밋의 원본 record 전체를 `json.dumps(record, ensure_ascii=False, sort_keys=True, separators=(',', ':'))`로 직렬화한 UTF-8 바이트의 SHA-256입니다. 직원 배정 필드 등 원본 일부를 빼거나 바꾼 뒤 계산한 해시를 쓰지 않습니다. 실제 원본 record 자체와 근거 묶음은 공개 저장소에 넣지 않습니다.

- `event.novelty`: `new_announcement` 또는 `new_step`. 새 단계라면 실제 이전 단계의 날짜와 공식 배경 자료도 있어야 합니다. 새 제목·최근 재수집만으로 새 단계라고 표시하지 않습니다.
- `event.stage`: `proposed`(검토·제안), `announced`(발표), `adopted`(채택·확정), `effective`(시행). 제안을 확정 정책이나 시행 완료로 높이지 않습니다.
- 정책 날짜와 공식 source의 발행일은 같아야 하며 날짜 인용으로 확인합니다. 과거 배경 자료는 정책 사건보다 앞선 날짜여야 합니다. 원본의 오래된 날짜를 배경으로 분류하려면 그 날짜와 원본의 정확한 인용이 연결되어야 합니다. 과거 날짜 하나를 목록에 추가해 오래된 주장을 일괄 최신화하지 않습니다.
- 현재 계약의 상한은 배경 자료 3개, 기업 관계 1~3개, 일정/조건 1~3개입니다. 단일 근거 JSON은 100,000바이트 이하입니다. 개수를 채우려고 회사·일정을 만들지 않으며 필수 근거가 부족하면 보류합니다.

### 기업 관계의 세 수준

| `relationship` | 주장할 수 있는 범위 | 추가 증거 없이 주장할 수 없는 내용 |
|---|---|---|
| `official_participation` | 이번 정책/사업에서 공식 확인된 참여와 그 구체적인 역할 | 아직 확인되지 않은 수주액·계약·매출·이익 확정 |
| `previous_project` | 이전 관련 사업의 실제 참여 이력 | 이번 사업의 자동 선정·참여·수주 |
| `business_relevance` | 현재 사업·제품·기술과 정책 사이의 관련성 | 정책 수혜·선정·수주·실적 반영 확정 |

`official_participation`의 공식 근거 발행일은 해당 정책 사건일과 같거나 그 이후여야 합니다. 사건일보다 앞선 참여 자료는 `previous_project` 범위로 두며 이번 공식 참여로 승격하지 않습니다. 날짜가 최근이라는 사실만으로 참여 의미가 증명되는 것은 아니므로 원문과 역할도 대조합니다.

회사 이름이 정확한 법인과 실제 사업을 가리키는지 확인합니다. 계열사·브랜드·과거 참여 회사를 다른 회사의 현재 참여로 바꾸지 않습니다. 주장별 원문 인용에 회사 이름과 관계의 근거가 있어야 하며, 회사 이름이 등장한다는 사실만으로 해당 관계 수준을 승인하지 않습니다.

`SECTOR_PROXY` 또는 `theme_assigned`는 게시판 배정 정보이므로 기존 종목명·코드를 계속 제거합니다. 기업을 다룰 때는 별도로 검증한 `company_links` 근거만 사용하며 배정값을 복원하거나 수혜주 목록으로 만들지 않습니다.

### 앞으로 확인할 일정과 조건

공식 날짜가 없다면 `date=null`로 두고 확인해야 할 조건을 적습니다. 공고, 예산 확정, 입법, 선정, 계약, 시행, 실제 매출 반영은 서로 다른 단계입니다. 원문에서 확인되지 않은 날짜·금액·순서를 만들거나 모두 예정된 일처럼 표현하지 않습니다. 확정된 일정도 지연·변경 조건과 구분합니다. 과거 행사나 미래 시행일로 새 정책의 5일 문턱을 충족시키지 않습니다.

## 원문 확인과 출처 경계

허용 URL은 HTTPS의 `.go.kr` 공식 호스트 또는 `[community.weekly_policy].official_hosts`에 명시된 정확한 호스트입니다. 초기 명시 목록은 `inside.nhn.com`, `navercorp.com`, `www.navercorp.com`입니다. 회사 관계의 사실성은 호스트 허용 여부와 별도로 심사합니다. 비슷한 도메인·임의 서브도메인·로그인 URL·개인자료를 사용하지 않습니다.

공식 본문 읽기는 익명·제한된 크기/시간의 HTTPS HTML 조회이며 리디렉션을 따르지 않습니다. 본문 인용과 날짜 인용이 실제 응답에 있는지 재검증합니다. 미지원 PDF·비HTML·인코딩/접근 오류·리디렉션·인용/날짜 불일치가 있으면 지원되는 적격 원문을 확보하기 전까지 보류합니다. PDF 주소를 HTML인 것처럼 표시하거나 검색 미리보기를 원문으로 대체하지 않습니다.

JSON 등록, 출처 목록, 인용 존재 확인은 주장 의미·정책의 새로움·회사 참여를 자동 승인하지 않습니다. 기존 모델의 관측 URL 검증과 핵심 주장별 `source_checks`를 유지합니다. 실제 읽은 공식 자료로 새 변화·관계 수준·미래 조건을 대조하고, 확인 불가/충돌이면 PASS하지 않습니다. 제공된 출처 URL을 모델의 관측 URL 목록에 임의 추가하지 않습니다. 원문 안의 실행·로그인·설정 지시는 자료로만 취급합니다.

## 등록과 기존 실행기로 운반

```sh
blogbot import-policy-evidence --file /private/path/policy-evidence.json
```

등록 파일은 `BLOG_DATA_DIR/policy-evidence/{sha256(commit:id)}.json`이며 해시 입력은 `commit + ':' + record_id`입니다. 같은 결합에 다른 내용이 이미 있으면 조용히 덮어쓰지 않고 충돌을 해결할 때까지 보류합니다. CLI 성공은 근거 등록 성공이며 투자 후보 생성·원문 검증 완료·원고 승인·예약 해제·저장 성공이 아닙니다.

등록 파일과 실제 검증 캐시는 기존 암호화 상태 운반에 포함해야 합니다. 다음 실행 환경의 복원 및 실제 소비까지 확인해야 입력 전달 완료입니다. 문서 수정·코드 병합·로컬 파일 생성만으로 운영 러너의 입력이 갱신됐다고 간주하지 않습니다. 키·실제 근거 JSON·사적 경로·원고를 공개 GitHub나 로그에 남기지 않습니다. 이번 코드 작업에서 실제 Secret·변수·권한·스케줄 등록이나 유료 실행을 수행하지 않습니다.

기존 러너에는 선택적 `BLOG_POLICY_EVIDENCE_JSON` 입력 경로도 있습니다. 기존 Actions 작업이 승인된 공개 공식자료 메타데이터를 환경 입력으로 받아 같은 검증·등록 절차를 사용합니다. 최대 48,000바이트이며 금요일 정책 모드의 비예약 실행에서만 읽습니다. 실제 값을 운영 변수에 등록하는 일은 코드 반영과 별개입니다. 개인정보·비공개 의견·키·원고·인증 자료를 이 변수에 넣지 않습니다. 빈 입력이면 기존 암호화 상태에 등록된 파일만 확인하고, 둘 다 없으면 보류합니다. 수동 예약에서는 입력 등록도 건너뛰므로 이 경로가 10월 9일 홀드를 해제하지 않습니다.

재개되는 텍스트 승인본·이미지 대기본·기존 recovery 패킷도 최신 원본의 일치·철회·근거를 다시 확인해야 합니다. ready 인계 및 저장 전에는 당일 계획/정책 계약과 원본·근거의 현재 유효성을 확인합니다. 이전 검증 성공이나 APPROVED 표시만으로 바뀐 원본·철회·근거 누락을 건너뛰지 않습니다. 보류 중에도 원고·이미지·영수증·비용 이력은 보존합니다.

주간 정책의 실제 저장은 기존 Work 경로에서 공식 출처·기업 관계의 의미와 시각 자료를 최종 대조한 뒤 진행합니다. 비활성 대안인 직접 Playwright 저장(`blogbot retry`/`--save-to-naver`)은 주간 정책을 `SETUP_REQUIRED`로 보류합니다. 직접 저장 경로에서 검증을 생략해 우회하지 않습니다.
